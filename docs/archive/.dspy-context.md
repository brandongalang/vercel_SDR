# DSPy Setup

## DSPy Context

### Use Case Summary

This project is an outbound personalization prototype for SDRs and GTM interview review. The near-term presentation goal is to show that the drafting system is backed by an offline optimization loop that improves against real success signals over time, rather than by manual prompt tuning.

The DSPy-adjacent use case here is narrower than the full multi-stage research pipeline. The DSPy optimization target is the draft generator policy: given lead context, a top signal, and a prior draft, produce a stronger subject/body pair that optimizes for rep trust and positive response signals.

### Recommended DSPy Program Shape

Recommendation:

- Keep DSPy scoped to the **offline draft-generator optimization loop**, not the live research orchestrator.
- Keep retrieval, signal collection, and tools **outside** DSPy. Feed the optimized DSPy program a cleaned task context rather than asking DSPy to own the full agent loop.
- Treat the optimized unit as a **single focused program** with a stable I/O contract. That keeps evaluation legible and makes promotion decisions defensible.

Why this is the right first shape:

- The repo already has the right labels for offline optimization but not the infrastructure for a continuously mutating online-learning system.
- The current task is best understood as “optimize drafting policy” rather than “build a fully DSPy-native agent.”
- A narrower optimized unit is much easier to explain in an interview: outcomes feed the optimizer, the optimizer produces a frozen artifact, and the app serves that artifact.

Simplest rejected alternative:

- Rebuilding the entire multi-step research and drafting workflow as a DSPy agent or `dspy.ReAct` loop would be harder to evaluate and much less aligned with the current repo and demo goals.

### Suggested Signatures

Current recommended optimization signature:

```text
lead_context, top_signal, prior_draft -> subject, body
```

Recommended stable semantic meaning:

- `lead_context`: normalized company, persona, play, timing, and confidence context
- `top_signal`: the one signal the draft should open from
- `prior_draft`: optional baseline draft for continuity and diffing
- `subject`: short, signal-specific subject line
- `body`: concise first-touch draft with a clear implication and low-friction CTA

Recommended supervision contract for offline optimization:

```text
inputs: lead_context, top_signal, prior_draft
target output: final_sent_subject, final_sent_body
labels: clean_accept, edited, replied, positive_reply
```

Important recommendation:

- Treat the **final sent draft** as the gold target for optimization.
- For untouched approvals, `prior_draft` and `final_sent_draft` are identical.
- For rep-edited sends, the **edited sent draft** should become the supervised target.
- This is the cleanest way to let human judgment influence MIPRO without turning the system into a live prompt editor.

Future hypothesis-aware inputs should not directly overwrite the signature. Instead, represent them as compile-time data or policy metadata, for example:

```text
lead_context, top_signal, prior_draft, policy_hints? -> subject, body
```

Default recommendation:

- Do **not** add `policy_hints` to live inference yet.
- Keep SDR hypotheses as offline optimization inputs, not as ad hoc runtime knobs.

### Suggested Modules

Recommended minimum module set:

1. **DraftGeneratorProgram**
   - Single DSPy module for subject/body generation.
   - Optimized offline.

2. **Dataset Export / Normalization Step**
   - Converts approved/edited/replied jobs into training examples and labels.
   - Should distinguish between the original generated draft and the final sent draft.
   - Already substantially present in [scripts/export-dspy-dataset.ts](/Users/brandongalang/Documents/Vercel_SDR/scripts/export-dspy-dataset.ts).

3. **Offline Optimizer Runner**
   - Runs MIPROv2 now.
   - Produces a frozen artifact plus version metadata.
   - Already substantially present in [scripts/ax-compile.py](/Users/brandongalang/Documents/Vercel_SDR/scripts/ax-compile.py).

4. **Future Feedback Reflection Layer**
   - Not a runtime module.
   - A compile-time path that converts `editorNote` and structured SDR hypotheses into textual feedback suitable for GEPA.

### Data and Evaluation Readiness

Observed readiness:

- Stronger than average for prompt optimization because the repo already captures both dense and sparse labels.
- Dense signals:
  - `cleanAccept`
  - `edited`
  - `editorNote`
- Sparse / lagging signals:
  - `replied`
  - `positiveReply`

Observed current evaluation shape:

- The compile script uses a weighted objective over rep-trust and reply-style signals.
- That is a good fit for an MLOps-style offline optimization narrative.
- The main missing piece for a fuller MIPRO story is explicit persistence of the **final sent draft** as distinct from the original generated draft.

Minimum viable evaluation plan:

- Dev/train data: exported jobs with prompt version attribution, rep actions, and outcome labels.
- Primary optimization target: match the **final sent draft** for each historical job.
- Primary metric family: combine output alignment to the final sent draft with example weighting from trust/outcome labels.
- Secondary review slices:
  - by `angleType`
  - by account segment / play
  - by prompt version epoch
- Explicit failure review set:
  - stale or generic hooks
  - overfitted CTA patterns
  - drafts that earn clean accepts but weak positive replies
  - hypotheses that look persuasive to reps but do not survive outcome data

Threshold for moving beyond the current baseline:

- Continue using offline optimization only if new candidates beat the current frozen artifact on held-out recent data and do not materially regress key review slices.

Recommended example-value weighting:

- `cleanAccept` = strong rep-trust signal
- `edited` = useful human correction signal
- `positiveReply` = highest-value market validation signal

Recommended interpretation:

- full accepts teach “the model already got this right”
- edited-into drafts teach “this is what the model should have said instead”
- positive replies teach “this pattern should count more in future recompiles”

### Recommended Optimization Path

Recommended presentation and implementation stance:

1. **Center MIPROv2 in the story**
   - Best fit for “the system keeps improving as usage data accumulates.”
   - Inputs in practical terms:
     - student program
     - trainset
     - metric
     - prompt model
     - teacher model/settings
     - demo-count budget knobs
   - It is the right hero for the page because it optimizes the drafting policy, not just the example set.
   - In this project, the recommended MIPRO framing is:
     - optimize toward the **final sent draft**
     - weight examples by rep trust and market outcomes
     - promote only the candidate artifact that wins offline evaluation

2. **Treat BootstrapFewShot as historical context, not the main event**
   - Useful as a stepping stone or prior version story.
   - Not the primary presentation focus.

3. **Use GEPA as the future path for SDR-seeded hypotheses**
   - Best fit when feedback is textual and domain-specific.
   - Inputs in practical terms:
     - student program
     - trainset
     - valset
     - metric that can return score plus textual feedback
     - reflection LM
     - execution traces / trajectories
   - Best use here:
     - editor notes
     - failure reasons
     - SDR hypothesis statements like angle shifts, phrase bans, CTA guidance, or segment-specific messaging observations

Recommended interpretation of SDR contribution:

- SDRs should **not** directly edit the live prompt.
- SDRs should contribute **exploration inputs**:
  - strong rewrites
  - angle ideas
  - CTA ideas
  - phrase bans
  - segment-specific messaging hypotheses
  - free-text explanations of why a draft missed

How those map to optimizers:

- strong rewrites -> candidate demos -> Bootstrap-style selection or MIPRO demo search
- broad policy ideas -> candidate instructions / policy hints -> best long-term fit with GEPA reflection or structured MIPRO experiments
- editor notes and failure reasons -> best fit with GEPA

Recommended operational pipeline:

1. Generate drafts with the current frozen artifact.
2. Persist both the original generated draft and the final sent draft.
3. Collect rep trust signals and lead outcomes.
4. Export labeled jobs and textual notes.
5. Build compile examples where the **target output is the final sent draft**.
6. Recompile on a cadence offline, not per-message.
7. Evaluate candidate artifacts on held-out recent data.
8. Promote only metric-winning candidates.

Key recommendation for interview framing:

- Describe this as an **offline closed-loop optimization pipeline**, not as online self-editing prompts.

### First Implementation Milestone

For the presentation page and the next engineering step, the first milestone should be:

- Reframe the UI around a **feedback loop**:
  - production traffic and outcomes in
  - offline optimizer run
  - frozen artifact promotion
  - live system updated on the next cycle
- Make `MIPROv2` the primary optimizer shown on the page.
- Omit Bootstrap from the main page narrative unless needed as brief historical context.
- Add a smaller “human exploration inputs” lane that explains:
  - SDRs can propose hypotheses
  - those hypotheses enter evaluation/optimization
  - metrics still decide promotion
- Explain clearly that MIPRO is learning from:
  - untouched approvals
  - what reps edited drafts into
  - actual positive lead responses

If implementation follows the presentation:

- Next concrete code milestone would be to formalize a schema for SDR hypothesis capture and `editorNote` normalization so those signals can eventually feed a GEPA-style compile path.

### Open Risks and Unknowns

- The current repo exports `editorNote`, but it does not yet define a structured feedback taxonomy. GEPA works best when textual feedback is consistent enough to reflect over.
- It is still unresolved whether SDR hypotheses should be stored as free text, controlled tags, or both.
- Compile cadence is not yet fixed. The presentation should avoid implying continuous real-time adaptation unless a clear offline schedule exists.
- There is still a risk of overstating what MIPRO currently uses. In the present repo, MIPRO is optimizing against exported labels and structured inputs; it is not yet consuming a rich human-hypothesis channel.
- The current repo does not yet show a first-class `final_sent_draft` field in the exported optimization dataset, even though that is the clearest supervision target for the next iteration.
- If the live page shows only optimizer names without the artifact-promotion loop, stakeholders may misread the system as manual prompt tuning rather than MLOps-style policy optimization.
